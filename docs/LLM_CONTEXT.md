# LiveSpace — LLM Context

macOS live wallpaper app. Plays a rotating playlist of local videos as the desktop background, with best-effort lock-screen sync. Ships as a signed `.dmg`.

## Xcode project

Managed via `xcodegen` (`project.yml` at repo root, NOT hand-edited in Xcode). After any source file add/remove or build-setting change:

```bash
xcodegen generate
xcodebuild -project LiveSpace.xcodeproj -scheme LiveSpace -configuration Debug build
```

`LiveSpace.xcodeproj` is generated output — don't hand-edit it, edit `project.yml`.

Signing: team `CL53882GFX` (the real paid team — the "N7U58LXWC7"-labeled certs in this user's keychain are cosmetically named but actually issued under CL53882GFX; confirmed via `openssl x509 -subject`, OU field is ground truth). No Developer ID Application cert exists yet — Debug/Release both sign with "Apple Development", so distributed dmg needs right-click→Open once (Gatekeeper).

## Targets

- **LiveSpace** (app) — the actual product. Everything below lives here unless noted.
- **LiveSpaceSaver** (`.saver` bundle, `ScreenSaverView` subclass) — built, embeds into the app's Resources, but **not wired into the active feature set**. Discovered mid-project that macOS's "Show as wallpaper" toggle only works for Apple's own built-in screensavers, not third-party `.saver` content — so this doesn't achieve desktop wallpaper. Left in place as a dormant option (installable via Settings) in case classic screensaver-while-idle behavior is ever wanted, but the real desktop wallpaper mechanism is the `NSWindow` overlay (below).
- **LiveSpaceWallpaperExtension** — **removed from project.yml, source files kept on disk** (`LiveSpaceWallpaperExtension/`). Was a from-scratch reverse-engineered ExtensionKit `.appex` targeting the private `com.apple.wallpaper` extension point, built to properly integrate with the lock screen the way Apple's own Aerial extensions and the competitor app Wallspace do. Got as far as: extension registers with the OS (needs `com.apple.security.app-sandbox` entitlement — that was the actual gate, not a special private entitlement), and `WallpaperAgent` connects to it. Blocked by a real tooling gap: `ExtensionFoundation`'s `AppExtension`/`PrimitiveAppExtensionScene` API has zero compile-time SDK artifacts (no `.tbd`, no `.swiftmodule`) in this machine's Xcode 26.6 install, even though the runtime framework exists in the OS's dyld shared cache. Wallspace's own extension was built with Xcode 26.2, which apparently had proper SDK support. Reviving this needs a different Xcode/SDK, not more code. Full reverse-engineered `WallpaperExtensionXPCProtocol` (21 methods, extracted from Wallspace's shipped binary via `nm`/`otool -ov`) is preserved in `WallpaperExtensionXPCProtocol.swift` if resumed later.

## Desktop wallpaper — how it actually works

No public API exists for third-party video wallpapers on macOS (confirmed via research — this is universal, every app in this category including Plash and Wallspace does the same thing).

- `WallpaperWindow.swift` — one borderless `NSWindow` per `NSScreen`, positioned at `desktopIconLevel - 1` (behind icons, above the true desktop picture layer), playing an `AVQueuePlayer` + `AVPlayerLooper` via `AVPlayerLayer`. Auto-pauses when `occlusionState` isn't `.visible` (fullscreen app covering it, hidden Space) — real battery win, don't remove.
- **Dark mode**: `dimLayer` (black `CALayer`, sits above `playerLayer`) darkens the video (opacity `0.35`) when `NSApp`/window `effectiveAppearance` is `.darkAqua`. Detected via `WallpaperHostView.viewDidChangeEffectiveAppearance()` (AppKit calls this on the content view automatically on live Light/Dark toggle — no manual notification observer needed). Deliberately a visual dim on the same video, not separate light/dark video files — chosen over per-video pairing to avoid requiring users to supply matching dark-mode assets.
- `WallpaperEngine.swift` — owns the per-screen windows, rebuilds on `NSApplication.didChangeScreenParametersNotification`, exposes `pauseAll()`/`resumeAll()` for lock/unlock.
- `RotationController.swift` — single `Timer` (20s tick) drives: reads `~/LiveWallpapers` (or user-chosen folder) fresh every tick via `ConfigStore.playlist(for:)`, advances `currentIndex` when `intervalSeconds` has elapsed since `lastAdvanced`, reloads video + syncs poster/lock-screen only when the index or playlist actually changed (cheap no-op otherwise). Also reachable via `RotationTrigger.shared.forceTick` for instant manual jumps (see `AppState.jumpToVideo`, `AppState.nextVideo`).
- **Rotate-when-video-ends mode** (`rotateOnVideoEnd` in `PlaylistConfig`, off by default): instead of looping one video for a fixed `intervalSeconds`, each video plays once and advances the moment it finishes. `RotationController.tick()` skips its interval-based advance when this is on; `WallpaperEngine`/`WallpaperWindow.setVideo(loop:onEnded:)` skip building an `AVPlayerLooper` and instead play the item once, firing `.AVPlayerItemDidPlayToEndTime` → `WallpaperEngine.onVideoEnded` → `RotationController.advanceOnVideoEnd()`. **Only `windows[0]` (the primary screen) gets the `onEnded` callback** — with N screens all playing the same file from the same start, every window would otherwise fire "ended" near-simultaneously and cause N-1 duplicate skips. Measured: no CPU/RAM regression vs. interval mode — same per-switch reload cost (~1-2s spike to 20-30% CPU for the new `AVPlayerItem`/asset load), just triggered more often since real video lengths (~13-27s here) are much shorter than the old 300s default interval.
- **Manual "Next Video"** (`AppState.nextVideo()`, wired into both the Settings picker row and the menu bar) — advances to the next playlist entry immediately regardless of mode, via the same `RotationTrigger.forceTick` path `jumpToVideo` uses.
- **Resume same video after app/system restart already works with no extra code** — `currentIndex` is written to `config.json` on every rotation (interval, end-of-video, or manual), and `RotationController`'s very first `tick()` on launch reads that value and loads it. Deliberately *not* tracking exact playback position/seconds across restarts (considered and reverted — added real complexity, i.e. a periodic checkpoint timer + `applicationWillTerminate` hook + a `resumeSeconds` seek path threaded through `WallpaperEngine`/`WallpaperWindow`, for a feature that was never actually requested — user only wanted "resume the same video," not "resume mid-frame"). If mid-frame resume is ever wanted, that reverted design is the shape to redo, but don't build it speculatively.
- **Menu bar/Dock chrome staying in sync** (`PosterFrameSync.swift`) — the real system Desktop Picture (`NSWorkspace.setDesktopImageURL`) is kept updated with a still frame extracted from whatever video is currently playing, every rotation. This is why the menu bar/Dock vibrancy shows *matching* colors instead of a stale unrelated wallpaper — a real limitation even Plash doesn't work around (confirmed via their own GitHub issues: "Plash is not actually a wallpaper... menu bar adapts its color from the actual system wallpaper"). **Keep the last-2-posters pruning logic in `pruneOldPosters`** — deleting the previous poster too eagerly (single-file prune, no buffer) caused a real race where the menu bar briefly referenced a deleted file. Poster set only prunes old files *after* confirming `setDesktopImageURL` succeeded on every screen.

## Lock screen — fragile, opt-in, honestly described in the UI as "experimental"

No public API. Mechanism: macOS caches a downloaded Apple Aerial wallpaper's `.mov` at `~/Library/Application Support/com.apple.wallpaper/aerials/videos/<id>.mov`. We overwrite that file's *content* with an HEVC-transcoded copy of the user's current video (same id, same path — the file macOS already has permission/reference to), back up the original once, and `killall WallpaperAgent WallpaperAerialsExtension` to force a reload.

- `LockScreenSync.swift` — the swap/backup/restore logic. `HEVCTranscoder.swift` — transcodes to HEVC `.mov` via `AVAssetExportSession`, disk-cached by source path+mtime under `~/Library/Application Support/LiveSpace/HEVCCache/`.
- **Requires the user to have already downloaded ≥1 Apple Aerial wallpaper** (System Settings → Wallpaper) — that's what seeds the slot we hijack. `LockScreenSync.hasDownloadedAerial()` checks for this and the UI surfaces a message if missing.
- **Only works reliably right after a fresh `killall`.** Empirically found: video shows on lock screen only ~2-3% of the time if you just wait for the natural 5-minute rotation tick to kill/relaunch the extension — the extension appears to cache decoded content in memory and only re-reads from disk on relaunch. Fixed by `ScreenLockObserver.swift`, which listens for the `com.apple.screenIsLocked` distributed notification and forces a fresh `killall` (`LockScreenSync.refreshOnLock()`) at the exact moment of locking, not just periodically.
- Even with a fresh reload, video may not appear *instantly* on lock — the lock screen shows a static frame first and only switches to live video after the system's screensaver idle-delay elapses (same delay as "Start Screen Saver after X minutes" in Screen Saver settings). We lower this system-wide value (`defaults -currentHost write com.apple.screensaver idleTime -int 5`) as a workaround — **this affects the user's regular unlocked-desktop screensaver too**, worth remembering if they complain about the screensaver triggering too fast while working.
- Tried and abandoned patching `~/Library/Application Support/com.apple.wallpaper/Store/Index.plist` directly (the approach a reference open-source project uses) — on this exact macOS 26 (Tahoe) build, every "Idle" entry in that plist is just a generic `"default"` color-provider placeholder, unrelated to the actual Aerial/screensaver selection. That plist is not where the real selection state lives on this OS version; never found where it actually is. Don't re-attempt without new evidence.
- Cold-boot poster (`/Library/Caches/Desktop Pictures/<GeneratedUID>/lockscreen.png`, matching what the reference project does) is implemented in `LockScreenSync.updateColdBootPoster` but **silently no-ops** — the parent directory is root-owned (`/Library/Caches/Desktop Pictures/`, mode 755) and only pre-exists for users macOS has already created a per-UID folder for; we can't `mkdir` it without root. Non-fatal, just means that specific fallback poster never updates for this user. Not worth chasing further.

## Shared utilities

- `ConfigStore.swift` / `PlaylistConfig.swift` — single JSON file at `~/Library/Application Support/LiveSpace/config.json`. Not sandboxed, not App-Group-based — deliberately simple since desktop app and lock-screen sync all run in the same process. When adding a new persisted field: add to `PlaylistConfig`, update the custom `init(from:)` decoder with `decodeIfPresent(...) ?? default` (NOT plain `decode`) for backward compatibility with configs written before the field existed, and add it to `.default`. Same rule applies to `ScreenConfig` (below) — its own fields need the same `decodeIfPresent` treatment for anyone who customized a screen before a newer field existed.
- `ScreenID.swift` (`NSScreen.stableID`/`displayName`) — per-screen identity, keyed off `CGDirectDisplayID`. **Not always stable**: confirmed live that an external display waking/reconnecting can hand back a *different* `CGDirectDisplayID` than it had before (observed going from id `1`→`3` mid-session with no user action, matching known macOS behavior for hot-plug/GPU-output re-init — the built-in display's id stayed put). Practical effect: a per-display override (folder/pattern/order) keyed to the old id silently stops applying and that monitor falls back to the default/mirrored group until re-customized — not a crash, just a quiet reset. Don't design anything that assumes a screen's id survives a sleep/wake or replug.
- `DebugLog.swift` — plain-file async logger at `~/Library/Application Support/LiveSpace/debug.log`. **Use this over `NSLog`/`os_log`** for anything you'll need to actually inspect — the unified logging system (`log show`) proved unreliable for this app's own messages during development (queries with `--predicate` and grepping for our log text repeatedly returned nothing even when the code definitely ran, for reasons never fully diagnosed — possibly OS log level filtering or subsystem defaults). `DebugLog` sidesteps that entirely.
- `WindowOpener.swift` — AppKit-owned Settings window shown/reopened from the menu bar. **Not** SwiftUI `WindowGroup`/`openWindow` — that was tried first and `ContentView.onAppear` never fired at all (root cause never fully diagnosed, suspected conflict with the custom `NSApplicationDelegate` + early `NSStatusItem` creation). `AppDelegate` now owns the single `NSHostingController`-wrapped window directly and the app's `Scene` is just an empty `Settings { EmptyView() }` placeholder to satisfy `App`'s requirements.
- `RotationTrigger.swift` — shared closure singleton letting `AppState` force an immediate rotation tick (used by the "jump to video" picker) without AppState needing a direct reference to `RotationController`.
- `LaunchAtLogin.swift` — thin `SMAppService.mainApp` wrapper. Registered automatically on first-ever launch (`UserDefaults` flag gates it to once).
- `MenuBarController.swift` — `NSStatusItem` (sparkles icon): Open Settings, Launch at Login toggle, Quit.

## Settings UI

Redesigned twice now — each time for real usability bugs, not just aesthetics.

**Second redesign** (current): the single-scroll layout became a 3-tab `TabView` once per-monitor/per-pattern settings pushed it past ~10 stacked sections — one long scroll mixing "where videos come from," "when/how they rotate," "how they look," "which monitor gets what," and "system integration" was hard to scan and made two competing rotation controls (the old `rotateOnVideoEnd` toggle and the order-pattern picker) sit side by side with no visual hint they interact.
- `ContentView.swift` — now just a thin `TabView` container (Playlist / Displays / Advanced), ~15 lines.
- `PlaylistSettingsView.swift` — the "default" scope: Now Playing, Video Folder, Rotation (Order + Switch-timing, shown/hidden rather than grayed out — `Switch` and the interval slider only appear at all when Order isn't Pinned, instead of rendering disabled), Appearance (Fill Style + start offset).
- `DisplaysSettingsView.swift` — one collapsed `DisclosureGroup` row per monitor (`"Fill · In Order · Default playlist"` summary line), expanding to the same controls as the Playlist tab, scoped to that screen. Collapsed-by-default was the actual fix for 2+ monitors turning the old inline-per-display blocks into a wall of duplicated controls.
- `AdvancedSettingsView.swift` — Screen Saver Plugin + Lock Screen, grouped together as the two experimental/rarely-touched integrations, out of the main flow.
- `SettingsUI.swift` — reusable pieces shared by all three tabs, **check here before adding a new settings control**: `SettingsSection` (icon + headline + card background, replaces the old private `section(_:)` view builder), `SettingsCaption` (secondary wrapping helper text — carries forward the `.fixedSize`/`.frame` fix from the first redesign, below), `LabeledSegmentedPicker` (`Label: [A|B|C]` row — exists because segmented `Picker(_:selection:)`'s built-in label doesn't reliably render on macOS outside a `Form`, same family of bug as the `Slider` issue below; every segmented picker in Settings goes through this rather than the labeled initializer).
- `PlaybackOrderPattern.label` renamed to plain-language terms (`In Order`/`Reverse`/`Shuffle`/`Pinned`) — the enum's `rawValue`s (`fromStart`/`fromEnd`/`random`/`static`) are unchanged for JSON compat, only the UI-facing label moved. A parallel `.explanation` property drives the one-line caption under the Order picker instead of a hand-written switch in the view.

**First redesign**: original GroupBox-based layout had real bugs, not just aesthetics:
- `Slider(value:in:) { Text("Interval") }` rendered that trailing label **inline next to the track** on macOS (unlike iOS where it's hidden), producing a stray "Interval" word in the middle of the row. Fix: use the label-less `Slider(value:in:step:)` initializer, never the labeled one, when a preceding `Text` already describes the control.
- Long caption `Text`s were truncating with "…" instead of wrapping — the surrounding `.frame(minWidth:)` on the container plus no explicit wrap-forcing on the `Text` let SwiftUI pick a single-line intrinsic layout. Fix: `.fixedSize(horizontal: false, vertical: true)` + `.frame(maxWidth: .infinity, alignment: .leading)` on caption text — now lives in `SettingsCaption`.
- No `ScrollView` originally — content could exceed the window's actual height with no way to reach it (no crash, just silently unreachable UI). Now every tab wraps its body in one.
- Custom `section(_:content:)` view builder replaced `GroupBox` for consistent header styling (`.headline` title above a rounded `.quaternary` background card) — GroupBox's default macOS styling read as cramped/inconsistent. Promoted to `SettingsSection` in the second redesign so all three tab files could share it.

## Performance (measured, not estimated)

Baseline via `top -pid <pid> -stats cpu,mem`, sampled over multiple 3-5s intervals while a video was actively visible on screen:
- **~3.5-6.6% CPU**, ~50-65MB RAM — consistent across a normal 4K/25MB video and a heavier 4K/36MB video. Hardware (VideoToolbox) decode confirmed — software decode would read 30-80%+, so this is already efficient at the codec level; further gains had to come from *when* it runs, not per-frame cost.
- Confirmed via live log correlation that `WallpaperWindow`'s occlusion-based pause and the lock/unlock pause (`WallpaperEngine.pauseAll/resumeAll`, wired in `AppDelegate` via `ScreenLockObserver`) actually fire and drop CPU to ~0% during those states — not just present in code, empirically verified against `debug.log` timestamps lining up with real lock/unlock events during a live session.
- Rotation-check `Timer` interval: 5s → 20s, cuts background wakeups 4x for negligible loss of rotation precision.
- **Per-video comparison** (both 3840×2160 H.264, hardware-decoded): `aurora-forest-night` (36MB, 13.95s, has audio track) ran ~5.8% avg CPU / ~47MB RAM; `penguin-ninja` (25MB, 12.4s, no audio) ran ~3.5% avg CPU / ~55MB RAM. **CPU tracks scene complexity/motion, not file size or resolution** — the smaller, audio-less file used less CPU despite being denser per-byte; RAM didn't correlate with either. Don't estimate a new video's cost from its file size — measure it (`top -l N -s 1 -pid <pid> -stats pid,cpu,mem`, desktop must be actually visible — see below).
- **Measuring correctly requires the desktop to be unoccluded.** The occlusion-pause optimization (above) means `top` reads ~0% CPU whenever another window/Space covers the wallpaper, which looks identical to "not decoding" — always confirm the desktop is actually showing (F11/Mission Control) before trusting a low reading, and take multiple 1s-spaced samples (`top -l 10 -s 1 ...`), not a single snapshot, since decode is bursty.

## Fixed: unnecessary WallpaperAgent restart on every rotation (heat/CPU complaint)

User reported the laptop getting hot while the app ran. First ruled out the obvious suspect — per-frame video decode — via live `top -pid <pid> -stats cpu,mem` sampling on the actually-running `/Applications/LiveSpace.app` process: 0-4% CPU, matching the existing documented baseline (above), so playback itself was not the cause.

Root cause found by reading `LockScreenSync.swift`/`RotationController.swift` together: `LockScreenSync.install()` was unconditionally calling `restartWallpaperAgent()` (`killall WallpaperAgent WallpaperAerialsExtension`) at the end of **every** rotation tick whenever `lockScreenEnabled` — not just at actual lock time. This is a real OS-level process kill+relaunch (agent restart + extension re-init), independent of and in addition to the cheap per-frame decode cost.

Checked the live config (`~/Library/Application Support/LiveSpace/config.json`) and found it made this far worse than the theoretical 300s-interval case: `rotateOnVideoEnd` was `true` alongside `lockScreenEnabled: true`, so real source videos (~13-27s each) were triggering this OS-agent kill+relaunch every 13-27 seconds continuously — dozens of times per minute — while the user was actively working and the lock screen was never even shown. That combination (both opt-in, independently reasonable) was never tested together before; the interaction is what actually produced the heat.

Fix: removed the `restartWallpaperAgent()` call from `install()`. The agent restart now only fires from `ScreenLockObserver.refreshOnLock()` at the real lock moment (below), which is the only time a fresh reload actually matters — the lock-screen file swap in `install()` (aerial slot file + cold-boot poster) still runs every rotation, it's just file I/O, no OS agent involved.

**Verified live, not assumed**: captured `WallpaperAgent`'s pid+start-time before rebuilding, then rebuilt, reinstalled the new binary to `/Applications/LiveSpace.app` (had to quit the old running instance first — Debug builds don't auto-update the installed copy), and re-launched. Sampled `WallpaperAgent` pid/start-time + `LiveSpace` CPU every 18s for ~6 minutes via a background loop logging to a scratch file. Result: one legitimate restart from an actual `com.apple.screenIsLocked` event (confirmed via `debug.log` correlation, pid changed exactly then), then 6+ subsequent rotation `install()` calls (every ~15-20s, `rotateOnVideoEnd` still on) produced **zero** further agent restarts — pid stayed constant across all of them. Confirms the fix: rotation no longer touches `WallpaperAgent` at all, only genuine lock events do.

**Takeaway**: when two independently-shipped opt-in features (`lockScreenEnabled`, `rotateOnVideoEnd`) combine, re-check the combined runtime cost empirically — don't assume each feature's individually-measured cost still holds when composed. This is also why the `## Performance` baseline above needs a caveat: it was measured with `rotateOnVideoEnd` off and doesn't cover the lock-screen-sync agent-restart cost at all, since that path didn't exist yet.

## Desktop widgets — investigated, likely not our bug

User reported desktop widgets (Calendar/Weather, pinned via macOS Sonoma+ desktop widgets) sometimes not visible. Researched before touching window-level code (changing `WallpaperWindow`'s level without evidence risked making it worse). Finding: Apple's own documented behavior is that desktop widgets get hidden/dimmed whenever *any* app window is considered active, independent of third-party wallpaper apps — by design, only reappear via F11 or "click wallpaper to reveal desktop." Our window sits at `desktopIconLevel - 1` and explicitly never takes key/main focus (`canBecomeKey`/`canBecomeMain` both `false`), so it shouldn't trigger the same hiding heuristic a real foreground app would. Left as an open question — proposed isolation test (quit LiveSpace, see if widgets still vanish) to the user but no confirmed verdict yet. If revisited: don't guess at window-level changes without first confirming via that isolation test whether LiveSpace is actually the cause.

## Feature backlog (not yet built, worth considering)

- **Manual light/dark video pairing** — the dark-mode dim overlay (above) is a visual treatment, not a video swap; a user who wants an actually different clip at night would need the "separate light/dark video per slot" design considered and declined in favor of the simpler dim approach.
- **Volume/audio support** — `queuePlayer.isMuted = true` is hardcoded in `WallpaperWindow.setVideo`; some source videos have audio tracks (confirmed: `aurora-forest-night...mp4` has AAC) that are silently dropped. Deliberate for a wallpaper app, but worth a toggle if ever requested.
- **Playlist reordering / drag-to-reorder in Settings UI** — order is implicit (filename sort); no UI to reorder without renaming files.
- **Weighted/duration-aware interval mode** — a hybrid between the two existing rotation modes: fixed interval, but capped at each video's actual length (so short videos don't loop pointlessly for the full interval, long ones don't get cut off mid-scene).
- **Exact mid-video resume across restart** — explicitly declined this session (see above); revisit only if actually asked for.

## Known non-goals / things not to re-attempt without new information

- Desktop "Show as wallpaper" native toggle for third-party `.saver` content — confirmed universally unsupported.
- Direct Index.plist "Idle" patching for lock screen selection — confirmed not where selection state lives on this OS build.
- Cold-boot poster directory creation without root — confirmed blocked by filesystem permissions.
- Rapid lock/unlock cycling (within 1-5s) will almost always show the static lock-screen fallback even with the fix working correctly — `killall`-triggered process restart has real latency (extension relaunch + first-frame decode). Not a bug; test lock-screen behavior by waiting 10-15s before checking, confirmed this resolves the "sometimes static" complaint when tested properly.

User asked about multi-monitor resource cost (2 screens, same video) — measured live: **no CPU increase** (5.5-6.4%, same as single-screen baseline) despite `NSScreen.screens.count == 2` confirmed and each `WallpaperWindow` running its own independent `AVQueuePlayer`. Followed up with a proper controlled test for *different* videos per screen: wrote a standalone harness (`dualtest.swift`, compiled and run outside the shipped app, deleted after) replicating the exact same window-level/player setup, played two genuinely different files simultaneously (verified via `lsof` showing both file handles open), measured again — still 4.2-6.4%, no change. Conclusion, and the reasoning behind it: Apple Silicon decodes video on a dedicated hardware block separate from the CPU cores; CPU only handles demuxing/orchestration, which costs the same regardless of stream content or count (up to that hardware block's concurrency ceiling, which 2 streams doesn't come close to). This is *why* per-screen independent playlists (declined earlier as a feature, see backlog) would be essentially free resource-wise if ever revisited — the earlier "would need its own per-screen state" backlog note is about engineering complexity, not a performance concern.
15. User reported the laptop getting hot with the app running. Ruled out video decode (still 0-4% CPU, matched baseline). Root-caused to `LockScreenSync.install()` unconditionally `killall`-ing `WallpaperAgent`/`WallpaperAerialsExtension` on every rotation tick, not just at lock time — and found the live config had `rotateOnVideoEnd: true` + `lockScreenEnabled: true` together, so this OS-agent kill+relaunch was firing every 13-27s continuously (see `## Fixed: unnecessary WallpaperAgent restart` above for full detail, verification method, and the composed-features lesson). Fixed by dropping the restart call from `install()`; agent restart now only happens on real `com.apple.screenIsLocked` events. Verified live via pid/start-time sampling across a rebuild+reinstall cycle — confirmed zero agent restarts across 6+ rotations post-fix, one correct restart on an actual lock event.
16. Added per-monitor customization: a `VideoRenderPattern` (Fill/Fit/Stretch — `AVLayerVideoGravity`) and a `PlaybackOrderPattern` (By Start/By End/Random/Static) can now be set per screen, independent of a per-screen playlist folder override. Architecture: `ScreenConfig` (new struct in `PlaylistConfig.swift`) holds one screen's full settings; `PlaylistConfig`'s existing flat fields became the "default" template every unconfigured screen falls back to (`effectiveScreenConfig(for:)`), so old configs and single-monitor users see zero behavior change. `RotationController` groups screens by `perScreen[id] != nil ? id : "default"` — customized screens rotate independently, uncustomized ones still mirror as one shared group exactly like before. `Static` forces `loop: true` regardless of the rotate-on-end toggle (so it never even attaches an end-of-video observer); `Random` picks a new index excluding the current one. Poster/lock-screen sync stays tied to whichever group currently drives `NSScreen.main` — the underlying mechanisms (`PosterFrameSync`, `LockScreenSync`) are still single-target, unchanged. **Confirmed live on real dual-monitor hardware** (built-in Retina + external 4K) that a customized screen and the default group actually run independently and don't fight each other — and incidentally reconfirmed the `ScreenID.swift` caveat above (external display got a new `CGDirectDisplayID` on wake mid-session, so its override silently didn't apply until re-set — a pre-existing hardware quirk, not something this feature caused).
17. User asked for a full Settings UI rewrite ("too confusing" — acting as UX/PM). Restructured from one long scroll into 3 tabs; see `## Settings UI` above for the file breakdown and reasoning. While live-testing on real dual-monitor hardware, hit a config-cleanup trap worth remembering: overwriting `config.json` from the shell *while the app process is still alive* races that process's own timers, which can re-write the file with its still-in-memory (pre-edit) state before it actually exits — the overwrite looked like it took (a `cat` right after confirmed clean content) but reverted minutes later once a background timer fired. Fix in practice: always confirm the process is actually dead (`pgrep`) *before* editing shared state files, not just before-and-after the edit. Also reconfirmed the pre-existing zombie `LiveSpaceWallpaperExtension.appex` (item 12) is still around and respawns with a new pid after the main app is killed — unrelated to this session's changes, not investigated further.
18. User asked what a newly-connected display defaults to and whether a "sync all displays" option exists — answering it surfaced a real bug item 16 introduced: `setRenderPattern`/`setOrderPattern` both materialized a *full* `ScreenConfig` override (freezing that screen's folder/interval/rotate-on-end as a snapshot) even when the user only touched Fill Style or Order — so the "Use a different folder for this display" toggle would silently show checked, and that screen would stop receiving live updates from the Playlist tab's defaults, purely as a side effect of a look/order change the user never asked to detach. Fixed by adding `ScreenConfig.customizesFolder: Bool` (defaults to `true` via `decodeIfPresent` for overrides persisted before the field existed, preserving their prior frozen behavior) — `effectiveScreenConfig(for:)` now returns folder/interval/rotate-on-end/start-offset *live* from the default template whenever `customizesFolder == false`, only `renderPattern`/`orderPattern`/the screen's own rotation index come from the override itself. `AppState`'s per-screen setters split accordingly: `setRenderPattern`/`setOrderPattern` materialize with `customizesFolder: false` (never flips an existing `true` back off), while `chooseFolder`/`setScreenInterval`/`setScreenRotateOnVideoEnd`/`setScreenStartOffset` force it `true`. Also added a "Reset to Default" button per display (`AppState.resetToDefault(for:)`, just removes the `perScreen` entry) as an explicit escape hatch — direct answer to "is there a sync option," since previously the only way back to fully mirrored was reconstructing the exact default values by hand. Verified live: changing only Fill Style no longer checks the folder toggle, and Reset to Default fully reverts a customized display in one click.
19. User reported the Displays tab's per-display rows only expanded when clicking the tiny chevron, not the row. Root cause: SwiftUI's `DisclosureGroup` on macOS only wires up its built-in disclosure triangle to toggle — a custom `label:` view's own `.onTapGesture` does *not* override that, `DisclosureGroup` intercepts the tap before it reaches the label's gesture recognizer (confirmed by testing: adding `.contentShape(Rectangle()).onTapGesture` to the label did nothing). Fixed by dropping `DisclosureGroup` entirely in `DisplaysSettingsView.swift` — each row is now a plain `Button(action: { isExpanded.toggle() })` wrapping the whole label (`.buttonStyle(.plain)`, manual rotating chevron `Image(systemName: "chevron.right")`), with expanded content shown via `if isExpanded`. Also promoted the row from a `@ViewBuilder` function to its own `DisplayRowView: View` struct — needed for `@State private var isExpanded` to actually survive `AppState`'s periodic `refreshDisplays()` re-renders (a free function has no stable identity to hang state off of). **Takeaway: don't trust `DisclosureGroup`'s custom label to be fully interactive on macOS — build the disclosure manually with a `Button` if the whole row needs to be clickable.** Rebuilt Release, reinstalled to `/Applications`, repackaged `build/LiveSpace.dmg` / `~/Downloads/LiveSpace.dmg`.
